Review the entire existing Laravel ERP codebase and all existing migrations related to Goods Receipt Notes, Inventory, Products, Warehouses, Storage Locations, Batches, Inventory Objects, and Inventory Movements before making changes.

The application is currently intended for staff working in a large retail shop. Purchase Orders are not required for the current operational flow. The primary inbound inventory document is therefore the Goods Receipt Note (GRN).

Implement the following inventory flow:

Goods are physically received → GRN is created → GRN is approved/posted → accepted quantities are automatically reflected in inventory.

1. GRN must work without a Purchase Order

The existing:

goods_receipt_notes.purchase_order_id
goods_receipt_items.purchase_order_item_id

should remain nullable.

A GRN must be fully valid when:

purchase_order_id = NULL
purchase_order_item_id = NULL

Do not make PO creation a prerequisite for receiving goods.

If a PO exists in the future, the GRN may optionally reference it.

2. GRN approval must create an inventory receipt

When a GRN is approved/posted, the system must process every GRN item and create the corresponding inventory receipt/movement.

For each item:

quantity_received
quantity_accepted
quantity_rejected

must be respected.

Only:

quantity_accepted

must increase available inventory.

Example:

Received: 100 BOX
Accepted: 98 BOX
Rejected: 2 BOX

Inventory must increase by:

+98 BOX

not +100 BOX.

3. Inventory movement must retain the GRN as its source

Every inventory receipt generated from a GRN must be traceable back to the originating GRN.

Use the existing inventory movement/reference architecture where appropriate.

Conceptually:

GRN-000001
↓
GRN Item
↓
Inventory Receipt / Movement
↓
Current Inventory

The inventory movement must identify:

movement_type = RECEIPT/PURCHASE
reference_type = GoodsReceiptNote
reference_id = GRN ID

Use the exact existing enum/string conventions in the project rather than introducing duplicate terminology.

4. Do not duplicate stock entry in the UI

The user must not have to:

create a GRN, and then
separately enter the same goods into Inventory.

The GRN approval/posting operation itself must trigger the inventory update.

The intended user experience is:

Create GRN
↓
Enter received items
↓
Approve/Post GRN
↓
System automatically updates inventory 5. Preserve the current inventory architecture where possible

Do not introduce a completely new stock architecture without first determining how the existing:

Reuse the existing architecture where it is appropriate.

However, identify and correct any structural problem that prevents ordinary received products such as tiles, sanitaryware, and other bulk-stock products from being properly reflected in inventory.

6. Distinguish ordinary stock from individually tracked inventory

Do not assume that every received product must become an individually identifiable inventory_object.

For example:

Kajaria Royal Gold 600×600
100 BOX

is ordinary/bulk inventory.

It should be possible to represent its stock quantity without unnecessarily creating one physical inventory object merely because a GRN was approved.

On the other hand, products such as granite/marble slabs may require individual inventory objects because each physical slab can have its own:

length
width
thickness

Therefore support the appropriate distinction:

Do not remove the existing inventory_objects functionality if it is required for slabs or other individually tracked inventory.

7. Granite/slab receiving

Preserve the existing:

goods_receipt_item_slabs

functionality.

When a slab-based GRN is approved, the actual received slab information must be reflected in inventory.

For example:

GRN
└── Granite Item
├── Slab 001 → 8 × 4 ft → 32 sq.ft.
├── Slab 002 → 7.5 × 4 ft → 30 sq.ft.
└── Slab 003 → ...

The corresponding inventory representation must preserve these physical measurements.

Do not reduce slab inventory to only:

quantity = 3

and lose the individual slab dimensions/area.

8. Warehouse and storage location

The inventory receipt generated by the GRN must use:

goods_receipt_notes.warehouse_id
goods_receipt_notes.storage_location_id

where applicable.

Therefore, after posting a GRN, the system must be able to determine:

Which warehouse/location received this stock?

Example:

GRN-000001
Warehouse: Main Warehouse
Location: A-01

ORO BIANCO
+20 BOX 9. Batch information

Review the existing:

goods_receipt_notes.batch_number

and all batch-related inventory migrations.

Do not assume that one GRN can contain only one batch if the existing domain model supports multiple batches.

If batch information logically belongs to the received item/inventory lot rather than the GRN header, adjust the design accordingly.

Do not unnecessarily delete existing batch functionality.

10. Quantity and unit handling

Review the existing unit/conversion architecture before changing anything.

GRN quantities must remain consistent with the existing:

units
unit_conversions
product_variants
inventory

architecture.

Do not create a second, competing unit-conversion system.

Also review whether:

quantity_received
quantity_accepted
quantity_rejected

being integer fields is appropriate given that the existing inventory movement structure supports decimal quantities.

If decimal quantities are required by the existing product/inventory model, modify the migration appropriately.

11. Approval must be atomic

GRN approval and inventory posting must occur within a database transaction.

The system must never leave the database in a state such as:

GRN = APPROVED
Inventory = NOT UPDATED

or:

GRN = DRAFT
Inventory = UPDATED

If inventory posting fails, the GRN approval must fail/rollback.

12. Prevent duplicate inventory posting

A GRN must not create duplicate inventory receipts if the approval/posting operation is accidentally submitted twice.

For example:

GRN-000001
Accepted = 20 BOX

must result in exactly:

+20 BOX

not:

+20 BOX
+20 BOX

Review the existing inventory movement/reference design and implement an appropriate idempotency/duplicate-posting safeguard.

13. GRN corrections/cancellation

Review the existing GRN status and inventory movement logic.

Once a GRN has been posted to inventory, do not simply modify its accepted quantity without considering the already-created inventory transaction.

If cancellation/reversal is supported, use an inventory reversal/adjustment transaction so that the inventory audit trail remains correct.

Do not silently delete historical inventory movements.

16. Expected final architecture

The resulting architecture should conceptually be:

                    Supplier
                       │
                       ▼
              ┌─────────────────┐
              │       GRN       │
              │ Goods Received  │
              └────────┬────────┘
                       │
                       │ Approval/Post
                       ▼
              ┌─────────────────┐
              │   GRN Items     │
              └────────┬────────┘
                       │
             ┌─────────┴──────────┐
             │                    │
             ▼                    ▼
      Ordinary Products      Tracked Products
             │                    │
             ▼                    ▼
      Stock Receipt          Inventory Object(s)
             │                    │
             └─────────┬──────────┘
                       ▼
              Inventory Movement
                       │
                       ▼
                 Current Stock

The core business rule is:

A posted/approved GRN is the source of an inventory receipt. The accepted quantity from the GRN increases inventory automatically, while the inventory transaction retains a reference to the GRN for complete traceability.

Important

Do not implement Purchase Order functionality as part of this change. PO support should remain optional because the current retail-shop workflow starts directly with GRN.
